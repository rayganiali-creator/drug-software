# 6. Security, consent, privacy, audit

* Every route is authenticated (fallback policy) and has a catalog permission: `safety.assess.run/read` (Patient, Physician, Pharmacist; dataScope medications), `clinicalrules.*` (above). Route patient id is authorized by ownership or an **active care relationship + consent** and an active patient record; the request body can name no patient. Refusals are one uniform 403 (no leak of "no such patient / not yours / no consent"); an assessment id of another patient is 404 on the caller's own route.
* **Per-category consent.** A professional needs consent for `medications`; `profile`, `allergies`, `symptoms` are each checked separately. A refused category is withheld: the input shows `NotAuthorized`, dependent rules report MissingData, findings needing it are not computed or are filtered out of stored views ("no match" on a withheld category would itself disclose it). Withheld categories are audited (`SAFETY_INPUT_BLOCKED`).
* The engine receives labels the requester may already read; the stored result contains medicine/allergy display names (same sensitivity as the record, same database). It never contains symptom text, notes, free text or identifiers other than record ids.
* **Audit** (hash-chained, tamper-evident only, not tamper-proof): `SAFETY_ASSESSMENT_RUN` (status, counts, rule-set, guidance state — no names), `SAFETY_ASSESSMENT_FAILED` (reason code), `SAFETY_INPUT_BLOCKED`, `CLINICAL_RULE_CREATED/SUBMITTED/REVIEWED/RETIRED/REFUSED`, plus `PATIENT_DATA_ACCESSED` when a professional reads. A test checks that a distinctive medicine name appears nowhere in the audit.
* No secrets, keys, network or external services; demonstration switches refuse to start outside Development/Testing; rate limit on writes; rule text screened for markup/links.
