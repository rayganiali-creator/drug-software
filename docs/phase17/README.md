## 2. Scope chosen and why

Evidence: the app had two parallel sets of pages for the same jobs. The real ones are server-authorized and tested; the sample ones look equally complete and one of them (`/adr`) shows a clinical-looking `causality` field that the product deliberately does not produce. The smallest safe subset that removes confusion without inventing endpoints:

1. **One adverse-event queue per professional (web).** The sample ADR pages and their duplicate menu entries are gone; old `/adr` links redirect to the stored queue (`/adverse-events`). The queue is the existing server flow: permission `adr.review`, per-patient relationship and consent, audit line, uniform 403.
2. **Dashboard tiles show the server's number only when it is known to be complete**, otherwise a dash. The queue endpoint reads the newest 200 open records of *all* patients and only then filters them to the ones the reviewer may read, so a capped read can miss records the reviewer may read, and a count made from the list would be too low (shown by a PostgreSQL-free HTTP test: an authorized older record is absent once 200 newer unrelated records exist). There is no existing total-count capability. The endpoint therefore now states in a response header, `X-Result-Truncated: true|false`, whether its read hit the cap (`true` also when exactly 200 were read). The body, authorization, filtering and audit are unchanged. The header is added to the CORS exposed headers (it is a non-sensitive boolean, and is set only on a successful, authorized answer). The tile shows the number only when the header is exactly `false`; a `true`, a missing header or any other value shows a dash with "Too many records to count here. Open the queue."; refusal, loading and not-connected states are as before. Each dashboard load writes the existing `ADR_ACCESSED` audit line (count only).
3. **Every sample-data page says so** (web and Flutter): "This page shows fictional records built into the app. It does not read the stored records, and nothing you do here is saved or sent", with a link to the stored-data page where one exists. Pages with stored data never show it.
4. **Care list → stored ADR records:** an active relationship now links to that patient's adverse-event records page (the server decides, as for the other links).
5. **The queue page warns when its list may be incomplete** (`ProAdverseEventQueue`, shared by the physician and pharmacist routes). It reuses `X-Result-Truncated`; no endpoint, permission, schema or dependency changed. `AdrApi.queueWithCompleteness` now also returns `completeness` (`queueCompleteness(header)`): header exactly `true` → `truncated` → warning "This list may be incomplete … Do not assume this list contains every open report." (`role="alert"`); exactly `false` → `complete` → no notice; missing or any other value (`maybe`, empty, `TRUE`, `1`) → `unknown` → "We cannot confirm this list is complete … Do not assume …". The records the server returned are still shown under the notice (the server already filtered them by relationship and consent); loading, error and refusal states are unchanged and show no notice. The notice does not say how many records are missing, because that is not known. New strings: `adr.queue.truncated.*`, `adr.queue.unknown.*` (Persian unreviewed, like all Persian text). The "all statuses" filter uses the same helper.

## 3. Security notes

* No endpoint, permission or authorization rule was changed or added; authorization is still decided only on the server. The client changes are display and navigation. A URL id typed by a user is never treated as proof: the stored pages call endpoints that check the actor's role, relationship and consent, and answer 403 identically for "no such record" and "not allowed" (existing tests: `Phase9ApiTests` – cross-professional isolation of the queue, patient and industry 403, unknown record id 403; `Phase15ApiTests` – no industry access).
* Redirects cannot widen access: `/app/physician/adr` and `/app/pharmacist/adr` stay under the role guard; a patient who opens them is refused by the area guard and by the endpoints.
* Organization isolation is unchanged (no pharmacy or industry code touched).

## 4. Not done (remaining mock or unavailable)

* **The queue is still capped.** The page now tells the reviewer so (section 2, item 5), but it does not page through or filter before capping, so records beyond the newest 200 open ones of all patients stay out of reach of this list. That needs a query change and is not done.
* Physician/pharmacist **patient lists, overviews, prescriptions, reports, review queue, patient questions, follow-ups** and all **pharmacy inventory/dispensing/requests/alerts** remain sample-only: no persistent backend exists (the inventory and prescription routes are static demo stubs). Building them needs new modules and decisions (prescribing authority, dispensing, e-prescription), none approved.
* Patient **home, check-in and profile** still run on sample data; the stored equivalents are reachable by link. Wiring the home hero to real doses is possible (existing endpoints) but larger.
* The check-in's two "urgent" symptoms and red alert are demo configuration, not sourced emergency criteria; they stay labelled as sample.
* No Persian review of the new strings (marked like all Persian text).
